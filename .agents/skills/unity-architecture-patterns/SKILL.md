# Unity 架构设计原则与设计模式工程规范指南

> [!IMPORTANT]
> **核心哲学：设计原则指引决策方向，设计模式解决具体问题，工程约束控制实现成本。没有一条原则或模式是绝对律法。**
>
> 必须根据项目的实际结构、体量规模、生命周期、性能需求、团队工作流、技术约束以及预期的“变化点”进行务实权衡。**严禁为了满足设计原则而机械抽象，严禁为了展示模式而引入设计模式。**

---

## 1. 架构决策与防过度设计流程

在引入任何抽象或模式前，严格遵循以下七步推演闭环：

```text
1. 识别真实变化点（Change Points：未来确定会频繁变动的轴向是什么？）
        ↓
2. 识别硬性约束（Constraints：帧率预算、GC分配、生命周期、团队理解成本）
        ↓
3. 预估系统复杂度（Complexity：该系统未来预计承载多少实体/规则？）
        ↓
4. 优先评估最简方案（Simple Solution：简单的 switch/enum/直接调用是否足够？）
        ↓
5. 评估候选模式/抽象（Pattern/Abstraction：哪个模式能精准隔离变化点？）
        ↓
6. 收益与代价权衡（Trade-offs：增加了哪些类和调用链？带来了什么收益？）
        ↓
7. 选择“最简充分设计”（Simplest Sufficient Design）
```

## 2. 八大设计原则（Unity 实战落地指南）

### 2.1 SRP — 单一职责原则 (Single Responsibility Principle)
一个模块/类应该有且仅有一个引起它变化的原因。
- **Unity 实践指南**：
  - 严禁出现上帝类（God Class）与巨型全局管理器（Oversized Manager）。
  - **切勿机械拆分**：不要把每一个只有三五十行的简单 MonoBehaviour 强行切碎为五六个微型组件。
  - **核心判定标准**：“这两个部分是否会因为完全不同的人、不同业务需求、在不同时间独立改变？”如果不会，保持合并反而内聚性更高。

### 2.2 OCP — 开闭原则 (Open/Closed Principle)
对扩展开放，对修改封闭。在稳定的系统核心中，已知的扩展点应优先通过新增代码而非修改核心逻辑来实现。
- **常用技术**：策略（Strategy）、工厂（Factory）、命令（Command）、状态（State）、装饰器（Decorator）、数据驱动（Data-driven）。
- **取舍红线**：OCP 不是绝对教条。对于分支极少且极其稳定的小型系统，清晰直观的 `switch (type)` 比一套冗长的接口+派生类层次结构更加易读、维护成本更低。

### 2.3 LSP — 里氏替换原则 (Liskov Substitution Principle)
派生类型必须能够完全替换其基类型，且不破坏原有语义契约。
- **禁忌与反例**：
  - 子类无法履行父类契约，或在覆盖的方法中抛出 `NotSupportedException`。
  - 子类要求比父类更苛刻的前置条件，或改变核心语义。
  - 仅仅为了复用几行代码而强行继承基类。
- **对策**：如果不是严格的“Is-A”语义，立即重构为组合（Composition）。

### 2.4 ISP — 接口隔离原则 (Interface Segregation Principle)
客户端不应该被迫依赖它用不到的方法。接口应当精简、聚焦。
- **Unity 推荐实践**：
  - 偏好职责单一的角色接口：`IDamageable`, `IHealable`, `ITargetable`, `IMovable`, `IRouteWindowHandler`。
  - 避免创建包含数十个无关 API 的臃肿大接口。
  - **反过度设计**：若某个类只有唯一的直接调用者，且短时间内无多态替换需求，不要机械地给每个类都提取一个 `IFoo` 接口。

### 2.5 DIP — 依赖倒置原则 (Dependency Inversion Principle)
高层业务逻辑不应直接依赖易变的低层实现细节，两者都应依赖抽象。
- **架构依赖方向**：
  ```text
  Gameplay (玩法业务层)
      ↓ 依赖
  Abstraction (领域契约/接口)
      ↑ 实现
  Infrastructure / Unity Engine / SDK / FileSystem (底层基础设施)
  ```
- **优秀抽象候选**：网络服务、存档持久化、平台 SDK、外部输入源、复杂算法、时间/随机数提供器。
- **避免教条**：不要为引擎核心基础组件或极其稳定的直觉工具类编写多余的无用接口。

### 2.6 LoD — 迪米特法则 / 最少知识原则 (Law of Demeter)
减少对象对其他对象内部结构的了解，只与你的直接朋友交谈。
- **典型反例**（链式深层调用）：
  ```csharp
  player.Weapon.Owner.Inventory.Manager.Service.DoSomething(); // 严重违背 LoD
  ```
- **改进**：通过直接协作对象提供具有明确业务含义的操作。
- **平衡点**：不要为了形式上的 LoD 在直接持有者上写几十个机械转发方法（Pass-through Methods）。

### 2.7 CARP — 合成/聚合复用原则 (Composition/Aggregation Reuse Principle)
**优先使用组合，次选使用继承。** 这与 Unity 本身的组件化（Component-Based）架构高度契合。
- **Unity 推荐范式**：
  ```text
  RoleEntity (GameObject)
  ├── MotorComponent (移动)
  ├── CombatComponent (受击/命中)
  ├── ActionController (动作/路由)
  └── StatusModule (状态/属性)
  ```
- **继承的合理场景**：类型层次在语义上严格符合“Is-A”；共享行为高度稳定；能够通过多态提供一致的生命周期管理（如 `ProcessBase<T>`、`CharacterStateBase`）。

### 2.8 DRY — 别重复你自己 (Don't Repeat Yourself)
DRY 针对的是**系统知识与业务规则**的重复，而不仅仅是表面相似的代码文本。
- **铁律**：**严禁为了消除三五行表面相似但演化原因完全不同的代码，去生搬硬套一个复杂的抽象泛型类或继承层级。**

## 3. 设计模式实用工具箱 (Unity Engineering Toolbox)

> 设计模式是解决特定痛点的方案模板，绝不是必须套用的框架模具。

### 3.1 创建型模式 (Creational Patterns)

| 模式 | 适用场景 (Unity) | 禁忌与反模式 | 替代方案 |
| :--- | :--- | :--- | :--- |
| **Factory Method** | 对象创建流程复杂；创建时机与具体子类型频繁扩展（如敌人生成、技能实例生成、Projectile 生成）。 | 简单 `new Foo()` 或直接 `Instantiate(prefab)` 时滥用工厂。 | 直接构造 / 预制体引用 |
| **Abstract Factory** | 需要创建一组必须保持风格兼容的族系对象（如不同风格阵营的角色+武器+特效全家桶）。 | 没有族系对象约束，纯粹为了创建对象而层层抽象。 | 简单工厂 / ScriptableObject 配置 |
| **Builder** | 对象构建具有极其繁琐的步骤、参数众多且构造顺序可选（如复杂技能管线上下文构建、网络封包组合）。 | 只有两三个参数的简单对象构建。 | 具名参数 / 配置结构体 |
| **Prototype** | 运行时快速克隆、模板实例化（如基于 ScriptableObject 模板克隆运行时数据副本、Prefab 运行时克隆）。 | 混淆浅拷贝与深拷贝；误以为克隆 Unity Object 会自动复制底层托管资源。 | 显式 DeepClone / 纯数据容器反序列化 |
| **Singleton** | **全局唯一、跨场景、强生命周期**的底层服务（AudioService, SaveService, InputService）。 | **单例地狱**：每个系统都写单例（UIManager, PlayerManager...），形成无法解耦的全局网状依赖。 | 局部注入 / Service Locator / 依赖传递 |

### 3.2 结构型模式 (Structural Patterns)

| 模式 | 适用场景 (Unity) | 禁忌与反模式 | 替代方案 |
| :--- | :--- | :--- | :--- |
| **Adapter** | 适配第三方 SDK、遗留旧接口转换、多平台 API 统一包装（如广告 SDK、平台成就、手柄输入驱动）。 | 为完全受控且单一来源的内部稳定代码写适配层。 | 直接修改或重构内部接口 |
| **Bridge** | 两个正交维度独立变化（如：动作逻辑维度 ↔ 动画驱动方式 URP/Spine）。 | 只有单一变化维度，强行拆桥导致类数量翻倍。 | 简单组合 |
| **Composite** | 树状层次结构，要求容器与叶子节点提供一致的接口（如 UI 树、技能复合节点树、行为树组合节点）。 | 扁平结构没有嵌套层级时强行使用。 | 扁平数组 / List 驱动 |
| **Decorator** | 运行时动态叠加包装行为（如基础伤害 -> 暴击修饰 -> 属性附魔修饰 -> 护盾吸收修饰）。 | 包装链路过深导致断点调试极其困难、调用栈爆炸。 | 数据驱动修饰器 / 管道式流水线 (Pipeline) |
| **Facade** | 为庞大复杂的内部子系统提供高层简洁的对外门面（如 `BattleFacade` 整合伤害、顿帧、音效、命中特效）。 | 门面本身承载过多具体业务逻辑，蜕变成新的上帝对象。 | 保持门面纯粹作为转发与调度器 |
| **Flyweight** | 大规模对象共享海量不可变数据（如 ScriptableObject 配置、共享网格/材质、技能静态配置资产）。 | **致命失误**：不小心在 Flyweight 共享数据中修改了可变实例运行时数据，导致所有实例被连带污染。 | 严格分离配置资产与运行时数据结构 (`RuntimeData`) |
| **Proxy** | 延迟加载（Lazy Loading）、资源虚拟化、远程调用拦截、权限与访问控制（如 Addressables 资源代理）。 | 对轻量级直接持有的资源强加代理层。 | 直接引用 / 智能指针封装 |

### 3.3 行为型模式 (Behavioral Patterns)

| 模式 | 适用场景 (Unity) | 禁忌与反模式 | 替代方案 |
| :--- | :--- | :--- | :--- |
| **Chain of Responsibility** | 请求需经过多个可能独立处理或拦截的节点（如受击判定管道：招架阻断 -> 闪避无敌 -> 护盾吸收 -> 最终伤害扣除）。 | 处理节点无明确终止条件导致无限传递；或节点之间存在强状态耦合。 | 显式管道 Pipeline / 中间件机制 |
| **Command** | 将操作封装为命令对象（支持输入捕获、重放、Undo/Redo、技能预输入排队、网络帧同步指令）。 | 简单的直接调用也要大动干戈封装成 Command 对象。 | 委托 (Action) / 直接方法调用 |
| **Interpreter** | 领域特定语言 (DSL)、复杂技能公式表达式解析、对话条件解析。 | 仅为了判断一两个数值大小强行写 AST 语法解析器。 | 硬编码函数 / 简单参数表达式 |
| **Iterator** | 自定义复杂遍历语义。 | C# 已自带极其高效成熟的 `IEnumerable<T>` 与 `IEnumerator<T>`，绝不重复造轮子。 | 原生 foreach / 数组索引 |
| **Mediator** | 多个对象之间网状密集通信，通过中介者进行收敛协调（如战斗、UI、音效三者协作）。 | 中介者膨胀为超级上帝对象，掌控过多具体实现。 | 事件总线 (EventCenter) / 明确的消息信道 |
| **Memento** | 状态快照保存与恢复（如战斗重放快照、撤销重做、局内 Checkpoint）。 | 误以为直接保存 UnityEngine.Object 引用就是快照。 | 纯 C# 数据快照结构体 / 序列化二进制 |
| **Observer** | 一对多的事件解耦通知（C# Event、GameplayEvent、消息总线、UI 数据绑定）。 | **生命周期泄漏**：忘记在 `OnDestroy` / `OnDisable` 注销事件导致内存泄漏与空指针异常；调用链隐蔽难以追踪。 | 强生命周期订阅器 / 显式回调接口 |
| **State** | 复杂的有限状态机（如角色移动状态、战斗行为状态、Boss 阶段 AI）。 | 状态只有两三个、转移极其简单时过度创建大量 State 类。 | 枚举 + switch 状态机 |
| **Strategy** | 同一算法在不同情境下可无缝替换（如不同怪物的索敌算法、不同伤害类型的计算公式）。 | 为一两行仅有微小差异的代码创建一堆策略类。 | 委托策略 (Func/Action) / 简单分支 |
| **Template Method** | 算法整体执行骨架稳定，但特定环节留给子类自定义（如技能执行管线：Check -> Prepare -> Execute -> Finish）。 | 继承层级过深导致基类修改处处暴雷；或步骤变动过于频繁。 | 管道模式 / 策略组合模式 |
| **Visitor** | 数据结构稳定但操作该结构的操作频繁新增（如技能编辑器节点校验、导出器、运行时构建器）。 | 数据节点类型本身还在频繁增删改动时滥用访问者。 | 直接在节点类上添加扩展方法 / 接口 |

## 4. 原则与模式权衡矩阵 (Trade-offs Matrix)

当做出重大架构推荐时，必须向用户清晰阐述以下权衡矩阵：

| 模式/手法 | 获得的收益 (Benefit) | 牺牲的原则或代价 (Cost / Trade-off) | 何时该妥协？ |
| :--- | :--- | :--- | :--- |
| **单例 (Singleton)** | 全局唯一性、确定性生命周期、访问极度便捷。 | 削弱 DIP（难以替换）、破坏测试隔离、破坏 LoD。 | 核心基础设施（如音频引擎、存档中枢、时钟中枢），全局确实只有一份。 |
| **观察者 (Observer)** | 极低直接耦合，易于多方监听扩展，满足 OCP。 | 执行控制流变隐式，排查问题成本高；需严格管理注销生命周期。 | 多模块对同一事件关心（如角色阵亡触发 UI、音效、关卡任务联动）。 |
| **装饰器 (Decorator)** | 避免派生类爆炸，支持运行时动态自由拼装新能力。 | 引入冗长嵌套调用栈，调试排查与对象归属感知成本增加。 | 动作修饰器、伤害修改层、网络流包装。 |
| **策略 (Strategy)** | 算法自由替换，易于单测，严格遵守 OCP。 | 类型数量膨胀，增加了对象分配与间接调用开销。 | 算法逻辑复杂且频繁新增/替换（如 AI 决策逻辑、路径寻路算法）。 |
| **中介者 (Mediator)** | 消除网状复杂依赖，集中管控协作时序。 | 中介者易沦为高耦合上帝对象。 | 密集网状通信子系统（如 UI 与战斗的边界交互）。 |
| **工厂 (Factory)** | 屏蔽复杂创建细节，解耦具体派生类型。 | 增加了抽象层和工厂类数量。 | 构建依赖注入复杂、或者根据配置动态决定实例类型。 |

## 5. 抽象时机与演进控制 (Abstraction Timing)

严格遵循代码演进的“三阶段法则”：

```text
阶段 1: 首次实现
  ↓ 专注于正确性与简洁性，直接编写最清晰的代码。严禁凭空预测“未来”。
阶段 2: 出现重复
  ↓ 观察实际变化，识别真正的重复模式（同一痛点出现 2~3 次以上）。
阶段 3: 确立边界并抽象
  ↓ 确认变化点的稳定边界，引入最小、最适度、最具表达力度的设计模式或抽象层。
```

- **核心准则**：
  - 当未来的变化方向尚不明确时：**保持代码简单，推迟抽象。**
  - 当相同的变化模式已经被事实证明并反复发生时：**引入最小充分抽象。**

## 6. 架构反模式排查清单 (Anti-Pattern Checklist)

在方案设计与 Code Review 时，使用以下清单对照排查：

1. **God Object（上帝对象）**：
   - ⚠️ 表现：一个类掌控游戏全局、角色状态、UI、音频、网络、存档、物理运算中的 3 项以上。
   - 🛠️ 治理：依据实际职责与独立变化原因，拆分为高内聚组件或独立 Service。
2. **Manager Hell（管理器地狱）**：
   - ⚠️ 表现：工程中到处都是 `XxxManager`，职责模糊，互相直接调用。
   - 🛠️ 治理：审视其实际职责，提炼为具体语义的 Component、Service、System、Repository 或 Controller。
3. **Singleton Hell（单例蛛网）**：
   - ⚠️ 表现：业务代码中随处可见 `FooManager.Instance.BarManager.Instance.Baz(...)`。
   - 🛠️ 治理：理清上下文与依赖传递，通过生命周期统一注入或上下文服务总线提供。
4. **Interface Explosion（接口爆炸）**：
   - ⚠️ 表现：为每一个仅有唯一实现的简单类都机械式配一个 `IFoo`。
   - 🛠️ 治理：剔除无替换价值的虚假接口，仅为跨层隔离（DIP）和多态替换保留真实接口。
5. **Design Pattern Explosion（模式过度堆叠）**：
   - ⚠️ 表现：一个简单的技能释放逻辑，强行拼凑了 Factory + Builder + Strategy + Decorator + Command + Observer。
   - 🛠️ 治理：奥卡姆剃刀，剔除多余间接层，回归直观易懂的最简实现。

## 7. 设计模式速查与选型决策树

```text
遇到以下痛点时快速检索：

[创建时]
• 复杂多步骤组装过程                      → Builder
• 需根据条件创建不同子类实例              → Factory Method
• 一整套风格互斥/相容的族系对象           → Abstract Factory
• 高频克隆带配置初始状态的模板            → Prototype
• 唯一的全局基础设施                      → Singleton (慎用)

[结构与解耦]
• 适配第三方/遗留不兼容接口               → Adapter
• 两个独立正交的轴向各自演化              → Bridge
• 树状/嵌套整体与部分一致对待             → Composite
• 运行时动态自由叠加能力                  → Decorator
• 为庞杂子系统提供简化门面                → Facade
• 极大数量实体共享大体量不可变数据        → Flyweight (注意运行时隔离)
• 延迟加载/虚拟代理/访问受控拦截          → Proxy

[行为与流程]
• 请求沿链式管道顺序过滤/拦截             → Chain of Responsibility (Pipeline)
• 请求/操作需排队、回退、网络同步         → Command
• 密集的网状多对多通信调度                → Mediator
• 局内快照存档与撤销重放                  → Memento
• 一处变化通知多方联动                    → Observer
• 复杂的角色/状态机流转                   → State
• 同一业务有多种可插拔算法实现            → Strategy
• 算法流程骨架固化，细节按步骤定制        → Template Method
• 数据节点稳定，需灵活扩展各种操作        → Visitor
• 技能规则公式/条件表达式求值             → Interpreter
```

## 8. 大型架构方案与 Review 标准模板

对于中大型架构设计、核心重构方案以及深度代码评审（Review），结构必须包含以下核心板块：

```markdown
## 1. 核心诉求与问题根因分析 (Problem Analysis)
深入分析痛点根因，说明现有设计在应对当前或未来需求时的阻碍。

## 2. 现有架构瓶颈与风险评估 (Current Architecture Issues)
指出调用链路混乱、职责越界、生命周期脱节或反模式等具体缺陷。

## 3. 变化点分析 (Change Points)
明确指出系统未来确定会扩展、变化的轴向是什么，保持不变的基座是什么。

## 4. 技术与工程约束 (Constraints)
列出 Unity 引擎生命周期限制、帧率/GC 预算、线程安全、持久化要求等硬性约束。

## 5. 方案对比分析 (Solution Options)
- 方案 A（最简保守方案）：说明其收益与局限性；
- 方案 B（适度抽象/模式方案）：说明其收益与引入的复杂度。

## 6. 设计原则与设计模式分析 (Design Principles & Patterns Evaluation)
论证选定模式的合理性，引用本 Skill 中的原则指导，杜绝无意义模式堆砌。

## 7. 原则与模式权衡透视 (Trade-offs)
明确说明“为了换取 [收益 X]，我们主动接受了 [代价 Y]”，论证合理性。

## 8. Unity 专属考量 (Unity Lifecycle, Performance & Memory Impact)
评估 MonoBehaviour 生命周期、GC 内存分配、Prefab/SO 序列化影响及资源释放闭环。

## 9. 最终推荐实施方案与落地方案 (Recommended Solution & Implementation Steps)
给出清晰、解耦的类图/数据流，以及小步推进的落地实施步骤。

## 10. 风险控制与可验证方案 (Risks & Verification)
列出潜在回退风险、排查手段，并给出确凿的自动化或实机可验证目标。
```
