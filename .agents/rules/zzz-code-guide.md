# ZZZ Unity 工程与架构指南

更新：2026-10-17。本文件为多个 Agent 共享的项目技术约定；各 Agent 的开发、测试与 Review 流程由其入口单独规定。Codex 由根 AGENTS.md 显式引用本文件，不依赖上面的宿主触发字段。

## 1. 使用原则

- 中文沟通、文档和注释，英文代码标识符；源代码、文档与配置以 UTF-8 读写。遵守根目录编码保护规则，严禁仅凭终端乱码覆写源文件。
- 按当前需求选择最简单且职责清楚的实现。原则和模式用于解决实际问题，不为满足模板增加接口、工厂、层级或防御代码。
- 正确性、维护成本、可理解性与性能结合当前场景权衡；性能结论需要实际测量。
- 计划与改动先核对受影响的调用方、状态、时间域和资源所有者；阅读范围随实际依赖扩展，不默认全项目审查。
- 本文规定目标边界，不宣称现有代码全部符合。发现存量偏差时记录具体位置，不借本次任务自动进行全局整改。

## 2. 目录与依赖边界

| 当前目录（Assets/GameClient 下） | 职责 |
| --- | --- |
| App | 组合根、初始化与关闭、主流程编排 |
| 2_Presentation | UI、相机、角色视觉与视听反馈 |
| 1_GamePlay | 实体、动作路由、战斗、移动、AI、队伍等玩法规则 |
| 0_Framework | 时间、事件、池、资源等基础服务 |
| Dependencies | 第三方依赖与自研可复用模块；各模块明确自身依赖 |
| Generate | 配置、协议等生成产物；优先修改数据源或生成器 |
| Tests | 对应模块的行为验证；测试入口按实际程序集配置判断 |

- App 负责组合；表现可消费玩法契约，玩法不引用表现层具体实现；Framework 不依赖具体玩法和表现。
- Dependencies 与 Generate 不是同一个抽象层。可复用模块声明必要依赖，禁止为复用基础能力反向绑定 ZZZ 业务类型或配表。
- 禁止模块/程序集循环依赖；Player 编译路径不得依赖 UnityEditor。编辑器功能放在 Editor 边界，或采用有效的条件编译。
- 命名空间采用稳定的模块语义并遵循周边约定；数字目录前缀不要求映射为命名空间。避免无理由的全局业务类型，不为路径一致批量重命名。
- 当前 ATEditor 核心负责时间轴数据与播放调度，默认 Unity 能力通过 Handler/服务契约接入并允许外部覆盖。输入、动作选择与路由保持独立职责；新结构需有具体需求与获授权方案。

## 3. 实体、配置与表现

- Manager/Service 管理服务与集合生命周期；Entity 持有身份、实例状态和能力；Controller/Module/Pipe 承担规则与算法；MonoBehaviour 接入必要的引擎生命周期。
- 这些是职责约定，不是强制的四层调用链。优先复用当前合适模块，避免为每个类机械增加中间层。
- 名称表达职责；保留既有模块命名习惯，允许 Director、Handler、Bridge、View 等合理后缀，不以统一后缀代替架构约束。
- 共享 SO、Luban、JSON 配置不存储每个角色的血量、冷却等易变状态。实例状态有明确所属对象和受控修改入口；不强制所有状态继承同一个基类。
- 核心战斗结果由权威规则决定，不依赖纯视觉反馈播放完毕。UI 可以提交用户意图；动画、VFX 和音效回调不私自修改血量、无敌或业务倒计时。
- 玩法通过契约请求表现；装配可以使用组合根、现有注册机制或明确的 Prefab 契约，不强制所有表现自注册工厂。
- 逻辑所需的动画姿态、根运动和检测采样属于明确的业务采样契约，不能仅因使用动画 API 就当作纯视觉反馈。

## 4. 时间与动作驱动

- 每个 dt、时间戳、速度和持续时长明确所属时间域，以及是否已经应用倍率。同一倍率只应用一次。
- 玩法使用调用者或实体时钟提供的逻辑步长；可复用 Runner 接受外部 Tick(dt)，不假设每个宿主都按本地固定 60 Hz 推进。
- 不在业务模块内另取全局 deltaTime 绕过实体时钟。表现服务可按明确的显示时钟独立更新，UI 可使用独立时钟。
- 默认动画/VFX/音频的表现更新不得额外推进动作逻辑、提交根运动或触发权威命中；逻辑采样与表现采样的边界按实际后端契约实现。
- 根运动位移是否需要缩放取决于动画采样时已经应用的倍率，不允许无条件再次乘 EffectiveScale。
- 预输入使用真实时间还是动作时间是玩法策略；保持现有确定行为，变更时明确慢动作、暂停及过期语义，不用通用规则替代设计决定。
- 倍率、暂停、Seek、停止与重播须有明确语义；仅当进入相应测试任务时执行验证，不由本条自动触发测试流程。

## 5. 所有权与生命周期

- 资源句柄、池对象、事件订阅、协程/Task 和播放会话明确：谁持有、谁使用、谁释放、何时失效。
- 所有者可以委托回收，但不能出现重复释放或失去责任归属。下层通过受控契约请求回收，不越权操作全局生命周期。
- Manager 可以持有其管理对象的引用；对象退出时移除相应引用与订阅，不把“禁止强引用”当作资源管理方案。
- 防止已销毁对象被异步完成回调重新登记；根据 API 能力使用取消、会话身份或完成时有效性检查，不强制所有 API 都必须新增 CancellationToken。
- 不吞掉有意义的异常；失败应能由负责的调用方观察和处理。无需为不存在的故障场景增加通用恢复框架。
- 对象出池、配置、激活和回收的顺序应有明确契约；保持 OnEnable 等消费者读取到本次有效状态。

## 6. 编码与维护

- 项目业务日志沿用 GLog 与模块标签；可复用 ATEditor 等模块采用自己的日志边界或可替换接口，不为统一日志反向依赖 GameClient 业务。避免高频无条件打印。
- 缩进 4 空格，C# 大括号沿用 Allman。优先最小必要可见性与 [SerializeField] private；对外集合根据修改权限提供只读或受控访问。
- 保留 GUID/meta 与序列化兼容性；修改类型、字段或程序集时检查实际资产与消费者。
- 第三方代码默认不改；生成产物优先通过源数据、模板或生成器维护。ATEditor 是自研模块，不因位于 Dependencies 就禁止修改。
- 全量编译、行为测试、Player 构建与性能验证是不同检查；何时执行由当前任务阶段与验收范围决定，不要求每次代码修改都自动全量运行。
- 只同步维护本次已确定变更涉及的条款；标明日期，不把未实施方案写成现状。不另建重复规则副本。
