# 动作指令执行架构全链路分析

更新日期：2026-03-31

## 1. 文档目标

本文从当前代码实际运行结果出发，完整梳理角色动作指令从输入产生到动作播放结束的全链路，并明确区分：

- 当前已经在运行的新设计
- 仍然保留并继续生效的旧设计
- 新旧并行、混合生效的部分
- 各类指令、各类方向、各类触发源的实际数据路径

本文不是“目标方案文档”，而是“当前落地实现文档”。

---

## 2. 核心结论

当前最新的动作指令执行架构不是纯新架构，也不是纯旧架构，而是一个**混合态架构**：

- 输入入口已经统一收口到 `CharacterInputEventAdapter -> ActionController.OnInput`
- 状态机上下文仍然是动作入口裁决的基础骨架
- 旧的 `LocalActionRoute + ContextRoute + Resolver` 仍在大量参与运行时决策
- 新的统一路由 `ActionRoute` 已经接管了：
  - 当前动作上的统一指令路由
  - 生命周期路由
  - 状态监控路由
  - Deferred 延迟执行
  - `ExecutionTarget` 执行目标
  - 路由集 `RouteSets`
- `CommandContextConfig` 目前仍然走旧式 `ContextRoute`，但已经支持 `ContextRouteSets`

因此，当前系统最准确的定义是：

> **“以 `ActionController` 为中枢的统一执行器 + 旧局部路由/上下文路由兼容层 + 新统一路由增强层”**

---

## 3. 总体拓扑

### 3.1 运行时主干

```text
InputActionSystem
->IInputProvider
  -> CharacterInputEventAdapter
    -> CharacterCommandFactory
      -> IInputCommandHandler
        -> ActionController.OnInput
          -> CommandBuffer
          -> 当前动作路由判定（旧 LocalActionRoute + 新 ActionRoute）
          -> 上下文路由判定（旧 ContextRoute）
          -> Resolver 解析目标动作
          -> RuntimeData 记录结果
          -> 状态机切换
          -> ActionPlayer 播放 Timeline
          -> ComboWindow / MotionWindow / OnComplete / StateMonitor 回流
```

### 3.2 主要责任分层

- 输入层：产生标准化指令和方向快照
- 缓冲层：在 0.3s 有效期内保留未消费指令
- 路由层：根据窗口、上下文、监控事件、生命周期事件决定下一动作
- 解析层：把“一个抽象指令”解析成具体动作资产
- 状态层：决定动作应该在哪个状态容器中执行
- 播放层：驱动 SkillTimeline、ComboWindow、MotionWindow
- 回流层：动作结束、窗口进入/退出、监控边沿触发后再次回到路由层

## 5.2 资源预热阶段

`ActionManager` 负责：

- 缓存 `SkillTimeline`

注意：

## 6. 输入到命令的标准化链路

## 6.1 输入源

接口：`Assets/GameClient/Input/IInputProvider.cs`

当前输入系统同时暴露两类信息：

- 轮询型状态
  - 当前方向
  - 上一帧方向
  - 是否有移动输入
- 事件型输入
  - 普攻按下/长按/取消
  - 特殊技按下/长按/取消
  - 闪避前/后/长按/取消
  - 大招
  - 交互

## 6.2 本地玩家输入实现

实现：`Assets/GameClient/Input/LocalPlayerInputProvider.cs`

关键点：

- `LightAttack.started` -> `OnBasicAttackStarted`
- `LightAttack.canceled` -> `OnBasicAttackCanceled`
- `LightAttackHold.performed` -> `OnBasicAttackHold`
- `SpecialSkill.started` -> `OnSpecialAttack`
- `SpecialSkillHold.started / performed / canceled` 被映射到特殊技长按事件
- `EvadeFront.started` 和 `EvadeBack.started` 分别触发两个事件

需要注意一个现状：

- 闪避输入在 `IInputProvider` 层仍区分前后
- 但进入 `CharacterCommand` 后会统一归并成 `CommandType.Evade`
- 前后差异最终不是靠 `CommandType` 区分，而是靠 `Resolver + DirectionSnapshot + HasMovementInput + 配置数组` 决定

## 6.3 输入适配器

实现：`Assets/GameClient/Logic/Character/Commands/CharacterInputEventAdapter.cs`

职责：

- 监听 `IInputProvider` 事件
- 将事件转换成 `CharacterCommand`
- 将命令交给当前状态的 `IInputCommandHandler`

映射规则如下：

| 输入事件 | 生成命令 |
| --- | --- |
| `OnBasicAttackStarted` | `BasicAttack + Started` |
| `OnBasicAttackHold` | `BasicAttack + Performed` |
| `OnBasicAttackCanceled` | `BasicAttack + Canceled` |
| `OnBasicAttackHoldCancel` | `BasicAttack + Canceled` |
| `OnSpecialAttack` | `SpecialAttack + Started` |
| `OnSpecialAttackHold` | `SpecialAttack + Performed` |
| `OnSpecialAttackHoldCancel` | `SpecialAttack + Canceled` |
| `OnUltimate` | `Ultimate + Started` |
| `OnEvadeFrontStarted` | `Evade + Started` |
| `OnEvadeBackStarted` | `Evade + Started` |
| `OnEvadeHold` | `Evade + Performed` |
| `OnEvadeHoldCancel` | `Evade + Canceled` |

空实现事件：

- `OnBasicAttackHoldStart`
- `OnSpecialAttackHoldStart`

说明：

- 这两个事件目前没有真正进主链路。
- 所以当前“长按开始”并不是一个独立可路由相位，真正进入中枢的是 `Performed`。

## 6.4 命令工厂

实现：`Assets/GameClient/Logic/Character/Commands/CharacterCommandFactory.cs`

创建命令时会写入：

- `Type`
- `Phase`
- `Payload.DirectionSnapshot = provider.GetMovementDirection()`
- `Payload.HasMovementInput = provider.HasMovementInput()`
- `Timestamp = Time.time`

这使得动作路由层即使在缓冲命令被延迟消费时，仍能读到“按下当帧的方向快照”。

## 7. 输入处理器层的现状

接口：`Assets/GameClient/Logic/Character/IInputCommandHandler.cs`

当前存在：

- `DefaultInputCommandHandler`
- `ComboInputCommandHandler`
- `DashInputCommandHandler`
- `NullInputCommandHandler`

但当前这几种 handler 的实质行为已经几乎统一：

- `DefaultInputCommandHandler` -> 转发到 `ActionController.OnInput`
- `ComboInputCommandHandler` -> 转发到 `ActionController.OnInput`
- `DashInputCommandHandler` -> 转发到 `ActionController.OnInput`
- `NullInputCommandHandler` -> 丢弃输入

因此：

- **旧时代“不同状态有不同输入处理逻辑”的结构还在类层面保留**
- **但新实现里真正的裁决已经收口到 `ActionController`**

这是一个明显的“旧壳保留，新核已统一”的过渡痕迹。

## 8. 命令缓冲与优先级链路

## 8.1 缓冲机制

实现：`Assets/GameClient/Logic/Skill/Combo/CommandBuffer.cs`

规则：

- 所有命令入缓冲列表
- 过期时间 `0.3s`
- `IsConsumed == true` 的命令会在 `Tick()` 中被移除
- 每次入缓冲都会分配递增的 `BufferOrder`

## 8.2 当前优先级行为

当前 `LocalActionRoute`、`ContextRoute`、`ActionRoute` 都有：

- `Priority`，默认 `0`

当前真正落地的竞争规则是：

1. 先枚举当前所有还有效的命令
2. 找出所有有效候选路由
3. 按 `Priority` 取最大值
4. 若 `Priority` 相同，则按 `BufferOrder` 取最新输入

也就是说，当前系统实现的是：

- **“执行时选最高优先级”**
- 而不是
- **“入缓冲时物理覆盖低优先级命令”**

因此对“预输入时低优先级不会覆盖高优先级”这件事，要精确理解为：

- 当前是通过候选选择规则保证高优先级优先执行
- 不是通过单槽缓存覆盖逻辑保证高优先级独占缓存

这点在阅读现状时必须区分清楚。

## 9. 状态机、上下文与动作入口

## 9.1 Ground 主状态

`CharacterGroundState` 进入时会根据：

- `PendingGroundEntry`
- 是否有移动输入

决定进入：

- `GroundIdleSubState`
- `GroundJogSubState`
- `GroundDashSubState`
- `GroundStopSubState`

## 9.2 各地面子状态设置的上下文

- `GroundIdleSubState` -> `GroundIdle`
- `GroundJogSubState` -> `GroundJog`
- `GroundDashSubState` -> `GroundDash`
- `GroundStopSubState` -> `GroundStop`

它们一边设置上下文，一边通过 `PlayStateAction` 播放基础 locomotion 动作。

## 9.3 Skill / Evade / Backswing / HitStun

- `CharacterSkillState.OnEnter()` -> `CurrentCommandContext = Skill`
- `CharacterEvadeState.OnEnter()` -> `CurrentCommandContext = Evade`
- `CharacterActionBackswingState.OnEnter()` -> `CurrentCommandContext = Backswing`
- `CharacterHitStunState.OnEnter()` -> `CurrentCommandContext = HitStun`

这四个上下文决定了：

- 当前命令是否优先走动作局部路由
- 当前是否允许上下文默认入口接管
- `CommandContextConfig` 查哪一组 `ContextRouteGroup`

## 9.4 RuntimeData 在链路中的职责

`CharacterRuntimeData` 维护：

- `NextActionToCast`
- `CurrentCommandContext`
- `CurrentLocomotionProfileId`
- `PendingGroundEntry`
- 最近一次命中的路由信息
- 闪避计数和冷却
- 受击硬直时长和方向轴

它既是“动作裁决输出寄存器”，也是“动作退出后的后续入口提示寄存器”。

## 10. ActionController：当前动作指令中枢

`ActionController` 是当前最新架构的实际执行核心。

它同时承担：

- 输入入口
- 缓冲命令扫描
- ComboWindow 响应
- 当前动作路由判定
- 上下文路由判定
- 生命周期路由判定
- 状态监控路由判定
- Deferred 路由轮询
- 状态切换
- 执行历史记录

### 10.1 每帧更新行为

`ActionController.Update()` 每帧做三件事：

1. `CommandBuffer.Tick()`
2. `StateMonitorEvaluator.Tick()`，收集本帧触发的监控事件
3. 若存在 Deferred 路由，则重测 `ExtraConditions`

### 10.2 接收输入

`OnInput(command)` 做三件事：

1. 命令压入 `CommandBuffer`
2. 若当前有激活的 combo window，则评估当前动作路由
3. 无论是否在动作窗口中，都评估上下文路由

这一点非常重要：

- **当前动作局部路由依赖窗口**
- **上下文路由可以在非窗口期生效**

## 11. ComboWindow 与局部动作路由链路

## 11.1 ComboWindow 类型

定义：`SkillEditor/ComboWindowClip.cs`

- `Buffer`
- `Execute`
- `Fallback`
- `RecoveryExecute`

## 11.2 进入窗口时的行为

`ActionController.OnComboWindowEnter(tag, type)`：

- `Execute / RecoveryExecute`
  - 立即对当前 tag 做一次路由评估
- `Buffer`
  - 清空当前命令缓冲
- `Fallback`
  - 切入 `CharacterActionBackswingState`

## 11.3 退出窗口时的行为

`ActionController.OnComboWindowExit(tag, type)`：

- `Buffer`
  - 在退出时把缓冲命令冲刷一次，对当前 tag 评估
- `Fallback`
  - 如果当前正处在 `Backswing`，优先尝试 `OnActionComplete`
  - 若没有生命周期接续，则回地面

## 11.4 当前动作路由来源

当前动作的命令路由会并行读取两套配置：

- 旧：`ActionConfigAsset.LocalRoutes + LocalRouteSets`
- 新：`ActionConfigAsset.Routes + RouteSets` 中 `Category == PlayerCommand`

具体执行时：

1. 读取当前动作
2. 展开 `LocalRoutes + LocalRouteSets`
3. 展开 `Routes + RouteSets`
4. 枚举所有未消费命令
5. 枚举所有允许立即评估的窗口
6. 找出所有有效候选
7. 根据 `Priority` 和 `BufferOrder` 选最好的一条
8. 立即执行，或进入 Deferred

## 11.5 当前动作拥有命令的判定

`CurrentActionOwnsCommand()` 当前会同时检查：

- 旧 `LocalActionRoute.MatchesCommand`
- 新 `ActionRoute.MatchesCommand`

用途：

- 如果当前动作已经拥有某个命令，就尽量不要让同一命令被上下文路由抢走
- 但在 `Backswing` 上下文中，会主动放弃这种“当前动作优先权”

这保证了 backswing 期的输入可以更容易走到默认上下文入口。

## 12. 上下文路由链路

## 12.1 上下文路由的来源

来源：`CharacterConfigAsset.CommandContextConfig`

调用链：

```text
ActionController.EvaluateContextRoutes
  -> CommandContextConfig.CollectEffectiveRoutes(CurrentCommandContext)
  -> 当前 ContextType 对应的 group
  -> group.Routes + group.ContextRouteSets
```

## 12.2 上下文路由何时被阻断

`ShouldBlockContextRoutes()` 的规则是：

- 如果当前没有激活窗口，不阻断
- 如果当前激活窗口里存在 `Fallback`，不阻断
- 其他有窗口但没有 `Fallback` 的情况，阻断上下文路由

等价理解：

- 动作正在正常可派生阶段时，优先让“当前动作自己的局部路由”接管
- 只有不在局部派生期，或者已经进入 backswing/fallback 语义时，才让上下文路由重新成为主入口

## 12.3 上下文路由当前仍是旧设计

当前 `CommandContextConfig` 仍然只支持：

- `ContextRoute`

它还没有切到 `ActionRoute` 统一模型。

所以当前上下文链路仍然是：

- 旧 `ContextRoute`
- 新增 `ContextRouteSets`
- 旧 `Resolver`
- 新增 `Priority`

即：**旧模型增强版，但还不是统一路由版。**

---

## 13. Resolver：抽象指令到具体动作的解析

定义：`Assets/GameClient/Logic/Skill/Combo/ComboTransition.cs`

当前只有两个注册解析器：

- `BasicAttackCommandActionResolver`
- `EvadeCommandActionResolver`

## 13.1 普攻解析器

规则：

- 如果路由里显式配置了 `NextAction`，直接用它
- 否则，如果当前上下文是 `GroundDash`
  - 返回 `CharacterConfigAsset.GetDashAttack(CurrentLocomotionProfileId)`
- 其他情况返回 `null`

这说明当前“地面冲刺普攻”实际上依赖 Resolver 做一次上下文补全。

## 13.2 闪避解析器

规则：

- 若路由显式指定了 `NextAction`，直接用它
- 否则检查 `CanEvade`
- 若命令携带了移动输入和方向快照，则优先前闪
- 否则优先后闪
- 若优先数组为空，则回退到另一方向数组

因此当前前闪/后闪不是靠两种不同命令来区分，而是靠：

- `CommandType.Evade`
- `Payload.DirectionSnapshot`
- `Payload.HasMovementInput`
- `CharacterConfigAsset.evadeFront / evadeBack`

联合决定。

## 14. 所有指令类型/方向的实际链路

## 14.1 BasicAttack

### Started

链路：

```text
输入事件 OnBasicAttackStarted
  -> CharacterCommand(BasicAttack, Started)
  -> OnInput
  -> 入 CommandBuffer
  -> 优先尝试当前动作路由
  -> 若未命中，再尝试当前上下文路由
  -> Resolver 可补全为 DashAttack
  -> 切状态并播放动作
```

特殊点：

- 如果当前处于 `CharacterSkillState` 且 `IsBasicAttackHold == true`
- 并且当前动作路由中存在 `BasicAttack + Performed`
- 那么 `BasicAttack + Started` 会被延迟，不立即参与这轮局部路由竞争

这就是当前“短按/长按冲突规避”的局部处理逻辑。

### Performed

典型用途：

- 长按普攻成立
- 由路由显式接出蓄力普攻/重击变体

### Canceled

典型用途：

- 结束按住状态
- 给部分动作一个“取消长按后的分支入口”

当前是否真正大量使用，取决于具体资产配置。

## 14.2 SpecialAttack

### Started

链路与普攻一致：

- 输入适配器生成 `SpecialAttack + Started`
- 进缓冲
- 当前动作路由优先
- 上下文路由兜底

### Performed

表示特殊技长按完成中的执行相位。

### Canceled

表示特殊技长按取消相位。

说明：

- `SpecialAttackHoldStart` 当前没有进中枢
- 真正可用于路由的是 `Performed / Canceled`

## 14.3 Ultimate

当前映射只有：

- `Ultimate + Started`

通常不会有 `Performed / Canceled` 路由来源。

## 14.4 Evade

### Started

来源有两条：

- `OnEvadeFrontStarted`
- `OnEvadeBackStarted`

但都统一映射成：

- `Evade + Started`

真正区分前后方向的环节不在输入适配器，而在 Resolver。

### Performed

来源：

- `OnEvadeHold`

可用于：

- 长按闪避延伸
- 闪避派生动作

### Canceled

来源：

- `OnEvadeHoldCancel`

### 前闪/后闪方向判定

当前前后闪的选择逻辑是：

1. 收到统一的 `Evade` 命令
2. 若路由显式指定 `NextAction`，直接执行该动作
3. 否则进入 `EvadeCommandActionResolver`
4. 读取命令方向和移动输入状态
5. 有方向输入则优先前闪，否则优先后闪
6. 若优先目标为空，再 fallback 到另一侧

因此，当前“前闪/后闪”是**解析阶段的方向分流**，不是**命令阶段的类型分流**。

## 14.5 Move

`CommandType.Move` 当前没有进入战斗动作中枢的事件流。

移动相关逻辑当前分布在：

- `GroundIdleSubState / GroundJogSubState / GroundDashSubState / GroundStopSubState`
- `StateMonitorEvaluator`
- `InputProvider` 的轮询方法

因此：

- Move 方向改变会影响地面状态切换
- Move 输入存在与否会影响监控事件和闪避/地面切换
- 但它目前不是一个通过 `CharacterCommandFactory` 投递进主链路的动作指令

## 15. 新统一路由链路

## 15.1 PlayerCommand 路由

`ActionRoute.Category == PlayerCommand`

作用：

- 与旧 `LocalActionRoute` 类似
- 但被统一纳入 `ActionConfigAsset.Routes`
- 可配 `ExecutionMode`
- 可配 `ExecutionTarget`
- 可纳入 `RouteSets`

当前消费入口：

- `EvaluateCurrentActionRoutes`
- `EvaluateTransitionsAgainst`

## 15.2 ActionLifecycle 路由

`ActionRoute.Category == ActionLifecycle`

触发时机：

- `CharacterSkillState.OnSkillEnd`
- `CharacterEvadeState.OnSkillEnd`
- `Fallback` 窗口退出后的 `OnActionComplete`

运行方式：

1. 当前动作播放结束
2. `ActionController.OnActionComplete(finishedAction)`
3. 收集该动作全部 `ActionRoute`
4. 只筛 `Category == ActionLifecycle`
5. 检查 `ExtraConditions`
6. 取最高 `Priority`
7. 若命中则直接接续下一个动作
8. 否则回到旧退出逻辑

这条链路是当前新设计里最完整、最明确的一部分。

## 15.3 StateMonitor 路由

`ActionRoute.Category == StateMonitor`

监控器定义：`Assets/GameClient/Logic/Skill/Combo/StateMonitorEvaluator.cs`

内置监控事件：

- `MonitorIds.LostMoveInput`
- `MonitorIds.GotMoveInput`
- `MonitorIds.DirectionFlip`

触发机制：

- 每帧比较当前状态与上一帧状态
- 只在边沿变化时发事件

当前默认监控内容：

- 移动输入从有到无
- 移动输入从无到有
- 输入方向突然大幅翻转，阈值约 170 度

运行链路：

```text
CharacterEntity.Update
  -> ActionController.Update
    -> StateMonitorEvaluator.Tick
      -> firedEvents
        -> EvaluateMonitorRoutes
          -> 当前动作的 unified routes
          -> Category == StateMonitor
          -> 选最高优先级
          -> 立即切动作
```

## 15.4 Deferred 路由

`ActionRoute.ExecutionMode == Deferred`

语义：

- 在 `Type + Phase + WindowTag + TriggerMode` 命中时先暂存
- 不立即要求 `ExtraConditions` 成立
- 后续每帧重测条件
- 条件成立时再真正执行目标动作

运行链路：

```text
输入命中 unified PlayerCommand route
  -> route.ExecutionMode == Deferred
  -> SetDeferredRoute
  -> 每帧 EvaluateDeferredRoute
  -> ExtraConditions 成立
  -> PlayActionDirect + UpdateCharacterState
```

这部分是旧系统完全没有的新增能力。

---

## 16. 旧局部路由链路

## 16.1 LocalActionRoute 的定位

旧 `LocalActionRoute` 仍然承担：

- 当前动作在特定 `ComboWindow Tag` 下的输入派生
- 判断 `RequiredType`
- 判断 `RequiredPhase`
- 判断 `RequiredWindowTag`
- 判断 `TriggerMode`
- 判断 `ExtraConditions`

当前仍被真正调用，不是历史废弃物。

## 16.2 LocalRouteSets

`ActionConfigAsset.LocalRouteSets`

作用：

- 给多个 `ActionConfigAsset` 复用同一份旧局部路由集
- 与当前 action 直配 `LocalRoutes` 并行展开

当前有效路由读取顺序：

1. `LocalRoutes`
2. `LocalRouteSets`

## 16.3 为什么说它是旧设计而不是废设计

因为它当前仍然直接参与：

- 当前动作指令命中
- 当前动作 owns-command 判断
- 普攻 hold-delay 逻辑

所以准确描述应是：

- **旧模型仍在线上生效**
- **但已经被新统一路由并行增强**

---

## 17. 动作播放与服务注入链路

## 17.1 ActionPlayer

职责：

- 切换动作时停止旧 runner
- 根据 `TurnMode` 在播放前矫正朝向
- 向 `ActionManager` 索取 `Timeline / Runner / Context`
- 调用 `SkillRunner.Play`
- 记录 `CurrentAction`
- 记录 `ActionStartTime`

## 17.2 ActionManager

职责：

- 缓存 `SkillTimeline`
- 缓存 `ProcessContext`
- 缓存 `SkillRunner`
- 统一预热角色动作资产

## 17.3 SkillServiceFactory

通过 `ProcessContext` 为 SkillEditor Runtime 提供服务：

- `ISkillAnimationHandler`
- `ISkillBoneGetter`
- `ISkillAudioHandler`
- `ISkillHitHandler`
- `ISkillVFXHandler`
- `ISkillSpawnHandler`
- `ISkillCameraHandler`
- `ISkillTransformHandler`
- `ISkillEventHandler`
- `ISkillComboWindowHandler`
- `ISkillMotionWindowHandler`

其中与动作指令架构最相关的是：

- `ISkillComboWindowHandler` -> `CharacterEntity.ActionController`
- `ISkillMotionWindowHandler` -> `CharacterEntity.SkillMotionWindowHandler`

也就是说，Timeline 运行过程中产生的窗口事件会直接回流到动作指令中枢。

---

## 18. MotionWindow 与 ComboWindow 的回流

## 18.1 ComboWindow 回流

Timeline 运行到 `RuntimeComboWindowProcess` 时：

- 进入窗口 -> `ActionController.OnComboWindowEnter`
- 退出窗口 -> `ActionController.OnComboWindowExit`

这是当前动作派生的核心回流点。

## 18.2 MotionWindow 回流

`SkillMotionWindowHandler` 负责把时间轴中的运动窗口效果回传给 `MovementController`：

- 启用/关闭 local delta filter
- 启用/关闭 visual offset
- 启用/关闭 visual offset recover

它不直接决定“接哪个动作”，但决定了动作播放期间位移表现如何被修正。

---

## 19. 动作完成后的出口链路

## 19.1 SkillState 结束

`CharacterSkillState.OnSkillEnd()`：

1. 拿到 `finishedAction`
2. 调用 `ActionController.OnActionComplete(finishedAction)`
3. 若生命周期路由命中，则直接接新动作
4. 否则执行旧退出逻辑：
   - `ApplyActionExitHints`
   - 回到 `CharacterGroundState`

## 19.2 EvadeState 结束

`CharacterEvadeState.OnSkillEnd()` 与 `SkillState` 一样：

- 先尝试统一生命周期路由
- 不成功再按旧退出逻辑回地面

## 19.3 ApplyActionExitHints 的作用

`ApplyActionExitHints(action)` 当前会处理：

- `LocomotionProfileOnComplete`
- `GroundEntryOnComplete`

这意味着动作本身可以决定：

- 结束后切到哪个 locomotion profile
- 结束后回地面时优先进 Idle / Jog / Dash

这是当前动作配置和地面状态机之间的桥。

---

## 20. Dash 特殊链路

Dash 是当前系统里最容易被忽略，但非常关键的一条分叉。

## 20.1 Dash 作为地面子状态

`GroundDashSubState` 本身就是地面大状态里的一个子状态，不是单独的 SkillState。

## 20.2 Dash 入口动作的双模式

`GroundDashSubState.StartDash()` 里存在一个特殊分支：

- 如果 `RuntimeData.NextActionToCast != null`
- 且该动作的 `ExecutionTarget == Dash`
- 则不是播放默认 DashStart locomotion
- 而是直接播放这个“指定要在 Dash 容器里执行”的动作

这意味着：

- 当前新统一设计已经允许“某个动作明确要求进入 Dash 容器执行”
- Dash 不再只是固定 locomotion，而是可以被动作路由动态驱动

## 20.3 DashAttack 的解析

如果输入是 `BasicAttack`，且当前上下文是 `GroundDash`：

- `BasicAttackCommandActionResolver` 会把它解析成当前 locomotion profile 对应的 DashAttack

所以 Dash 攻击目前依然深度依赖旧 Resolver。

---

## 21. HitStun 特殊链路

`CharacterHitStunState` 基本不走正常指令链路。

特点：

- 输入处理器是 `NullInputHandler`
- 进入时直接播放 `hitReactionConfig.hitAnimLight`
- 超时后自动回到 `CharacterGroundState`

这是当前系统里一条典型的“非命令驱动动作链”。

也说明：

- 当前动作播放架构并不只有“输入 -> 路由 -> 动作”一种来源
- 还存在“受击系统直接推状态并播放动作”的旁路链路

## 23. 当前系统的真实裁决顺序

把当前代码的真实顺序压缩成一句话，可以表达为：

> 输入先入缓冲，若当前动作存在可用窗口则优先尝试“当前动作路由”，若未命中再按当前上下文尝试“上下文路由”，命中后经 Resolver 解析出具体动作，写入 RuntimeData，切换状态并播放；动作播放过程中窗口、监控事件、生命周期结束会继续回流到同一个 `ActionController` 做下一轮裁决。

展开后的实际顺序如下：

1. 输入事件产生
2. 输入适配器创建 `CharacterCommand`
3. 当前状态的 handler 转发给 `ActionController`
4. `ActionController` 将命令压入 `CommandBuffer`
5. 若当前存在激活窗口，尝试当前动作路由
6. 若当前动作路由未接走，尝试上下文路由
7. 路由命中后经 Resolver 解析具体 `ActionConfigAsset`
8. `RuntimeData.NextActionToCast = nextAction`
9. 记录 `LastRouteSource / Context / Tag / ActionId`
10. 清空窗口和命令缓冲
11. 根据 `ExecutionTarget` 或动作类型切换状态
12. `ActionPlayer.PlayAction`
13. Timeline 运行时回调 ComboWindow / MotionWindow
14. 状态监控器每帧发边沿事件，可能再次切动作
15. 动作结束时尝试生命周期路由
16. 若无后续路由，则应用退出 hints 并回地面

## 24. 当前实现中最重要的“方向”维度

用户提到“所有类型/方向”，这里的“方向”在当前架构里主要有四种含义：

## 24.1 输入方向快照

来自：

- `CommandPayload.DirectionSnapshot`

用途：

- 播放前朝向
- 前闪/后闪解析
- 可能被条件、监控、位移逻辑消费

## 24.2 移动输入有无

来自：

- `CommandPayload.HasMovementInput`
- `IInputProvider.HasMovementInput()`

用途：

- 前闪/后闪分流
- 地面状态切换
- `LostMoveInput / GotMoveInput` 监控
- GroundEntry 的 `RequireMovementInput`

## 24.3 方向翻转事件

来自：

- `StateMonitorEvaluator.DirectionFlip`

用途：

- 动作中途因为输入方向大幅翻转而切到别的动作

## 24.4 动作执行容器方向

来自：

- `ExecutionTarget`

它不是空间方向，而是“状态机目标方向”：

- 去 `Ground`
- 去 `Skill`
- 去 `Evade`
- 去 `Dash`

这是当前新设计非常关键的一种“执行方向”。

## 25. 当前实现的风险点与注意事项

## 25.1 上下文路由还没统一

当前 `CommandContextConfig` 仍是旧 `ContextRoute`，因此：

- 上下文入口不能直接复用 `ActionLifecycle / StateMonitor / Deferred`
- 新旧两套配置心智仍然并存

## 25.2 路由优先级是“选择优先”不是“缓存覆盖优先”

如果有人按“单槽缓存覆盖”去理解当前优先级行为，会和实际代码不一致。

## 25.3 闪避前后方向在命令层已经被合并

如果后续要做“前闪 Started 和后闪 Started 完全不同路由”，当前命令模型还不够，需要：

- 新增命令类型
- 或新增方向枚举字段
- 或在路由层显式增加方向条件

## 25.4 InputHandler 类仍保留旧壳

这本身不是 bug，但容易让人误判“状态切换会改变大部分输入处理逻辑”。
当前实际逻辑大多已经统一收口。

## 25.5 RouteSets 的预热覆盖要持续确认

如果某个动作只存在于 route set 的 `NextAction`，且没有被别处引用，需要确认是否一定被角色预热链路收集到。

---

## 26. 最终结论

当前最新的动作指令执行架构，可以定义为：

> **以 `ActionController` 为统一执行中枢，输入经 `CharacterInputEventAdapter` 标准化为 `CharacterCommand` 后进入短时缓冲；当前动作局部路由、当前上下文默认路由、生命周期路由、状态监控路由共同参与动作决策；旧 `LocalActionRoute / ContextRoute / Resolver` 与新 `ActionRoute / ExecutionTarget / Deferred / Monitor` 处于并行工作状态。**

如果从成熟度看：

- 输入入口统一：已完成
- 状态机上下文骨架：稳定运行
- 当前动作路由统一：部分完成，新旧并行
- 上下文路由统一：未完成，仍走旧链
- 生命周期/监控/Deferred：新链已实装
- 资产复用层：`LocalRouteSets / ContextRouteSets / RouteSets` 已开始落地

因此当前系统最准确的阶段判断是：

> **“统一动作指令中枢已经成型，但还未完成对旧上下文路由和旧解析心智的完全替换。”**
